## 1. Environment

Services, from the repository root:

```bash
docker compose up -d postgres mosquitto      # treklink-postgres on 5432, treklink-mosquitto on 1883
npm ci
```

Backend variables (`.env` at the repository root, copied from `.env.example`; the backend loads
`backend/.env` and then `../.env`):

| Variable | Demo value | Why |
|---|---|---|
| `DATABASE_URL`, `DATABASE_DIRECT_URL` | `postgresql://postgres:postgrespassword@localhost:5432/treklink?schema=public` | The compose database. Both are required by `prisma migrate` |
| `MQTT_BROKER_URL` | `mqtt://localhost:1883` | The compose broker; `replay:mqtt` reads the same variable |
| `MQTT_INGESTION_ENABLED` | `true` (the default) | `false` runs the backend without a broker, and MF-02 and MF-03 then show nothing |

| `HANDOVER_NOTE_STORAGE_DIR` | `storage/handover-notes` (the default) | Where the signed handover note of MF-01 is stored, relative to `backend/` |
| `COMPANY_LEGAL_NAME`, `COMPANY_ADDRESS`, `COMPANY_TAX_CODE`, `COMPANY_HOTLINE`, `HANDOVER_PLACE` | the values chosen for the demo; the defaults are placeholders (tax code `0000000000`) | The letterhead and Party A of the handover note (rentals design §4.1) |
| `SEED_ADMIN_PASSWORD`, `SEED_STAFF_PASSWORD`, `SEED_MANAGER_PASSWORD`, `SEED_OPERATOR_PASSWORD` | chosen before the demo, never committed | `npm run seed:demo` refuses to run without all four |

Frontend: `VITE_API_BASE_URL=http://localhost:3000/api`, `VITE_WS_URL=http://localhost:3000`.

Start both: `npm run dev` (or `npm run dev:backend` and `npm run dev:frontend` in two terminals). The
frontend is on `http://localhost:5173`.

**Where the invitation code appears.** With `MAIL_TRANSPORT=console` the backend logs each email on a
`[Mail]` line: `from=... to=<email> subject="Your TrekLink invitation code" text="Your TrekLink invitation code is <code>. ..."`.
Search the backend terminal for `invitation code` and the recipient's address. A password reset reads
`Your TrekLink password reset code is <code>`.


The seed creates `admin@`, `staff@`, `manager@` and `operator@treklink.local` with the four

a roster shift, and contract RC-2026-0001 holding TL-0009 and TL-0010 (holder labels Le Thi E and Pham Van

**Wait before any replay.** The seed hands TL-0009 and TL-0010 over at the moment it runs. An event that
occurred within `gatewaySync.attributionMarginSeconds` (300 s in the migration seed) of a handover is
`UNATTRIBUTED`, so an SOS replayed sooner goes to `UNROUTED` instead of the Operator. Wait more than five
minutes after `seed:demo` before MF-02 or MF-03.

## 3. Parameter tweaks for the demo

The primary, backup and Manager acknowledge timeouts default to 120 s, 120 s and 180 s. Set each to 30 s
(the lowest the registry accepts) so MF-03 escalates in about 90 s. As `admin@`, use the **Parameters** page
(`/t/admin/parameters`, **Module** `incidents`, **Edit**, `30`, a reason, **Save**; treklink-web#216), or the
API below as a fallback (`PATCH /api/parameters/:key`, api-design of platform):

```bash
API=http://localhost:3000/api
TOKEN=$(curl -s $API/auth/login -H 'Content-Type: application/json' \
  -d "{\"email\":\"admin@treklink.local\",\"password\":\"$SEED_ADMIN_PASSWORD\"}" | jq -r '[.. | .accessToken? // empty][0]')
for key in incidents.primaryAckTimeoutSeconds incidents.backupAckTimeoutSeconds incidents.managerAckTimeoutSeconds; do
  version=$(curl -s "$API/parameters?ownerModule=incidents&pageSize=100" -H "Authorization: Bearer $TOKEN" \
    | jq -r --arg k "$key" '.result.items[] | select(.key == $k) | .version')
  curl -s -X PATCH "$API/parameters/$key" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"value\":30,\"expectedVersion\":$version,\"reason\":\"Demo 2026-11-01\"}" | jq -r .message
done
```

Run it once before the meeting; a refusal prints the server message. The login body is `LoginDto`
(`email`, `password`) of `POST /api/auth/login`, and the list filter is `ownerModule`.

## 4. Flows

### MF-01: register to signed handover

Browsers: a private window for the Guest and the new Manager, and one signed in as `staff@`.

1. Guest: `/register`, fill the organization and the Manager's contact, submit.
2. Staff: `/t/organizations`, open the new organization, record the documents seen (verify), then approve.
3. Backend log: copy the invitation code sent to the Manager's address (section 1).
4. Manager: `/welcome`, enter the email, the code and a new password, then sign in.
5. Manager: `/o/contracts/new`, choose a plan, a variant and at least the minimum order, set the start
   date to today, review and send. Submit is enabled as soon as the organization is ACTIVE, read from the
   API, with no second sign-in.
6. Staff: `/t/contracts`, open the request, approve it.
7. Staff: record the counter payment of the first invoice from the contract or `/t/billing`.
8. Staff: `/t/counter/<contractId>`, provision the devices, then take the handover signature.

### MF-02: live trek on the map

```bash
npm --prefix backend run replay:mqtt -- trek --now --new-ids --interval 2000
```

`trek` is TL-0009 (`!de000009`). `--now` shifts the timestamps to now, `--new-ids` gives each packet a
fresh id so a repeated demo is not deduplicated, and `--interval 2000` publishes one packet every 2 s.
Watch `/o/map` as `operator@` and `/t/map` as `staff@`.

### MF-03: SOS to escalation

Three browsers: `operator@`, `manager@` and `staff@`. Do section 3 first.

```bash
npm --prefix backend run replay:mqtt -- sos --now --new-ids
```

`sos` is TL-0010 (`!de00000a`) on RC-2026-0001.

1. The Operator (primary) gets the MSG31 banner, "SOS: TL-0010 (Pham Van F), hh:mm. Acknowledge now.",
   and the incident appears at `/o/incidents`.
2. Nobody acknowledges. After the primary timeout the incident moves to the backup tier (the Manager),
   then to the Manager tier, then to `ESCALATED`.
3. `staff@` gets the alert with an Open queue link, and `/t/incidents` lists the incident under
   "Unrouted and escalated" with its detail inline.
4. To close the flow: the Operator or the Manager acknowledges from `ESCALATED` at `/o/incidents/<id>`,
   then posts a status and resolves with an outcome note.

Escalation (steps 2 and 3) needs the timer jobs and the Staff recipients of treklink-web PR #120
(HoangTK, `IncidentTimersJob` with the D-079 Staff read). Without #120 the incident stays at
`NOTIFY_PRIMARY`; show step 1 and step 4 only.
